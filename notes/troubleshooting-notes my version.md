# Troubleshooting Notes
## 1. Understanding `ulimit -c`

Command:

```bash
ulimit -c
```

Observation:

```text
unlimited
```

Explanation:

This displays the core dump size limit for the current shell.

An unlimited value means that the shell does not impose a specific maximum core dump size.

However, core dump generation can still be restricted by process-specific limits, permissions, kernel configuration, resource availability, and the configured core dump handler.

Do not interpret `unlimited` as confirmation that core dumps are being generated.

## 2. Understanding the Kernel Core Pattern

Command:

```bash
cat /proc/sys/kernel/core_pattern
```

Observation:

```text
|/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h %d %F
```

Explanation:

The leading pipe indicates that the kernel sends core dump data to a handler rather than simply writing it to a conventional core file.

In this environment, the handler is systemd-coredump.

The presence of this configuration identifies the handling mechanism but does not confirm that a crash occurred.

## 3. systemd-coredump Socket Is Active

Command:

```bash
systemctl status systemd-coredump.socket --no-pager
```

Observation:

```text
Active: active (listening)
```

Explanation:

The socket is ready to receive core dump data.

An active socket does not mean that a core dump has been received or stored.

## 4. coredumpctl Returns No Records

Command:

```bash
coredumpctl list
```

Observation:

```text
No coredumps found.
```

Possible explanations include:

- No process crash generated a core dump.
- Core dump generation was restricted.
- The process terminated without producing a core dump.
- Previous core dump records were removed through retention or cleanup.
- The configured storage or handling mechanism differs from the expected location.

The result should be documented as no records found at the time of investigation.

## 5. Core Dump Directory Is Empty

Command:

```bash
ls -lah /var/lib/systemd/coredump/
```

Observation:

The directory existed but contained no files.

Explanation:

This is consistent with the empty coredumpctl listing.

However, an empty directory alone does not prove that a process never crashed. Storage configuration and retention behavior should also be considered.

## 6. Understanding Kernel Crash-Recovery Messages

Journal output included:

```text
crashkernel reserved
Starting Crash recovery kernel arming
Finished Crash recovery kernel arming
```

Explanation:

These messages relate to kernel crash-recovery preparation and reserved memory.

They should not be interpreted as proof of an application crash or a process core dump.

Kernel crash dump preparation and application core dumps are different mechanisms.

## 7. Interpreting Unrelated Wazuh Events

Observation:

Wazuh Discover returned a registry key deletion event from:

```text
DESKTOP-9MMM37V
```

Explanation:

The event originated from the Windows endpoint rather than the Rocky Linux server.

It was generated by Syscheck and described a registry key deletion.

This event is not evidence of Linux core dump activity.

Always verify the agent name, agent ID, event source, and timestamp before associating an alert with an investigation.
